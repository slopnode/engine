@page ecs_pipeline Systems and pipelines

The engine's runtime state lives in one `flecs::world`, owned by `App` (`src/game/app.hpp`). This page explains how that world is assembled and how a frame moves through it. See @ref systems for the full per-system reference table.

# The frame loop {#pipeline-frame-loop}

`App::run` (`src/game/app.cpp`) is a plain loop around `world.progress()`, called once per native window frame. There is no fixed timestep. Systems that care about elapsed time read `GetFrameTime()` themselves rather than take a delta argument from flecs. Ahead of `progress()`, the loop only handles map-load bookkeeping: starting or advancing a loading session, or swapping the loaded map outright. Everything else about a frame happens inside the systems `progress()` runs. The world is single-threaded. Nothing here sets a task or stage count.

# Modules {#pipeline-modules}

Each gameplay domain has a registration function, `registerXModule(world, ...)`, defined in `src/<domain>/<domain>_module.cpp`. It is a plain function, not a `flecs::module`. Each does three things in order: register that domain's component types, set up any singleton state the domain needs (a `PhysicsWorld*` handle, a query used by every render system, and so on), then register that domain's own systems and observers. `App`'s constructor calls every domain's `registerXModule` exactly once, in this order: input, UI, physics, sight, navigation, audio, camera, interact, particles, trails, render, loading session, underwater effect, the motored-body system, and script boot. Script boot loads the base game's own Scheme handlers on top of everything the engine itself just registered.

Flecs runs every system in a phase in the order it was added to the world, and this codebase relies on that instead of declaring explicit dependencies between systems. Input's `CaptureInputCommand` only feeds physics's `CharacterMotorInput` and camera's `FirstPersonController` correctly because the input module is registered first. The same mechanism has a sharper edge. Audio's `Sync3dAudio` reads each entity's world transform for spatialization, but it runs before render's `UpdateGlobalTransforms` recomputes that transform for the frame. Spatialized audio each frame is positioned off the previous frame's transform, one frame stale, and neither system shows that on its own. Moving a `registerXModule` call is a real behavior change, not a cosmetic reorder.

# Phases {#pipeline-phases}

Every system declares one of flecs' three built-in phases, `PreUpdate`, `OnUpdate`, or `PostUpdate`, through `.kind(...)` on the system builder. Nothing in this engine defines a custom pipeline phase. `PreUpdate` samples a frame's inputs and turns them into intent: polling devices, building the character motor's wish velocity, aiming the camera. `OnUpdate` is where the bulk of simulation happens: physics stepping, navigation replanning, interaction and trigger checks, particle simulation, animation advancement, and the Scheme tick hook. These are ordered relative to each other only by registration order, as above. `PostUpdate` is presentation: syncing eye-space viewmodel sockets, then the actual raylib/ImGui draw calls, bracketed by their own `StartDrawing`/`EndDrawing` systems. The render pass is just more of the same pipeline, not a special case bolted on after it.

# Writing a system {#pipeline-writing-a-system}

A system gets a string name as its first argument. Always spell one out. It shows up in a debug build's flecs explorer, and in `NAV[...]`-style log lines that key off `flecs::entity::name()`. From there it's `.each(...)` for anything that should run once per matching entity, with component references passed straight into the lambda, or `.run(...)` for singleton-style work that isn't really per-entity, such as polling raw input or ticking Scheme, where the callback receives the `flecs::iter` and reaches into world singletons itself. Component and singleton lifetime cleanup goes through observers instead of a system: `.observer(...)` with `.event(flecs::OnRemove)`. That way a moving-platform body or an audio voice gets torn down exactly when its component disappears, instead of being polled for it.

Nothing here is disabled at the flecs level to pause the game. There's no `entity.disable()` and no query-side filtering for it. Instead, individual systems check `isPlaying(world)` and `isSimulationPaused(world)` (`src/game/game_state.hpp`) at the top of their own body and no-op if either says stop. A paused system still matches and iterates every entity every frame. It just declines to act on any of them. The pipeline shape stays constant regardless of game state, at the cost of every gameplay system needing to remember the check itself.

# Scripting interleaving {#pipeline-scripting}

Package Scheme code meets the ECS two ways. One dedicated `OnUpdate` system, `CallSchemeTick`, calls the Scheme `tick` hook exactly once per frame, gated on `isPlaying && !isSimulationPaused` the same way any other gameplay system gates itself. This is the only per-frame heartbeat Scheme gets by default. Everything else is event-driven: individual systems call directly into Scheme mid-frame for their own event as it happens, not through `tick`. Examples are package action bindings on a pressed input, `on-crush` from a moving platform, `on-sight` from an actor's vision scan, and `on-use` from an interaction. A package handler for one of these fires inline, on whichever system's turn it is in that frame's phase order, not deferred to a script-only pass.
